# Desktop fork and integrated product-system recommendation

Research/design only, 12 November 2026. Baseline: `pingdotgg/t3code` revision **7d71f852a8edd298ffde67c295760c286a71a27c** (U). This supplements the existing pinned census, rather than repeating it. I read PRODUCT.md, docs/ARCHITECTURE.md, docs/plans/2026-11-12-open-product-studio.md and docs/research/t3-code.md. The latter two requested paths resolve beneath `docs/`. Public source and cached snapshots were inspected; no dependencies, application code, credentials, or provider sessions were executed. Recommendations below are proposed changes, not implemented capabilities.

## Decision: maintain a downstream T3 Code fork

**Fork the complete monorepo at U, preserve the execution platform and familiar chrome, and add a business-domain layer plus a dashboard main surface.** This directly meets downloadable Electron from the first executable milestone. The existing browser-first/original-UI proposal is superseded by the clarified requirement.

Selective reuse would require extracting mutually dependent contracts, Effect services, client state, provider lifecycle, approvals and desktop integration while recreating their UI glue. Greenfield gives architectural freedom but recreates precisely the difficult behavior the user wants preserved. Neither is justified here. Forking is feasible on source and license evidence; a successful clean packaged build remains the first implementation gate, not a research claim. Upstream already supplies desktop, web, server, provider packages, release tooling and an MIT license. [Repository](https://github.com/pingdotgg/t3code/tree/7d71f852a8edd298ffde67c295760c286a71a27c), [desktop package](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/apps/desktop/package.json).

## File-level integration surfaces

Preserve these existing surfaces unless a specific domain requirement forces a seam:

- `apps/web/src/components/AppSidebarLayout.tsx`, `Sidebar.tsx`, `sidebar/SidebarChrome.tsx`, `components/ui/`, and `index.css`: retain layout, controls, appearance and keyboard conventions; add module navigation inside that shell.
- `components/chat/ProviderModelPicker.tsx`, `ModelPickerContent.tsx`, `ProviderModelPicker.logic.ts`, and `apps/web/src/modelSelection.ts`: retain selector mechanics; inspect default resolution for the explicit no-fallback policy.
- `packages/contracts/src/modelSelection.ts`, `model.ts`, `orchestratorMcp.ts`, `packages/provider-core/`, existing provider packages, and `apps/server/src/orchestration-v2/`: retain protocol/lifecycle contracts instead of replacing them with the earlier simplified adapter proposal.
- `packages/client-runtime/`, `apps/server/src/ws.ts`, `persistence/Sqlite.ts`, and `persistence/DatabaseStorage.ts`: extend validated RPC and durable storage; do not introduce a parallel SSE execution engine.

Change `apps/web/src/routes/_chat.tsx` deliberately: it owns `ThreadRouteView` mounting, preserves the view through draft promotion, and overlays settings/usage. `_chat.$environmentId.$threadId.tsx` itself renders null. Merely replacing that leaf route misses the real seam. Add a project-dashboard route and proposed `features/studio/BusinessDashboard.tsx`; preserve conversations as activity/detail panels and optional full thread views. Maintain background-run and modal behavior. [Layout source](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/apps/web/src/routes/_chat.tsx), [UI conventions](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/docs/internals/web-ui.md).

New proposed boundaries are `packages/studio-contracts/`, `packages/studio-domain/`, `apps/server/src/studio/`, and `apps/web/src/features/studio/`. Keep business aggregates separate from provider threads. A business project references several T3 runs, artifacts and optional coding workspaces; it must not require a Git repository to exist. Names above describe verified paths except these explicitly proposed additions.

## Distribution, licensing and upstream ownership

Retain the complete T3 Tools Inc. MIT copyright and permission notice in redistributed substantial code, source and packaged notices. The license permits modification and commercial distribution; it does not require publishing modifications. Use distinct product branding and do not imply T3 endorsement. Audit bundled assets and dependencies individually: the tree includes `components/files/office/LICENSE.opencode` and license-generation tooling. Keep `scripts/sync-third-party-license-notices.ts` and the open-source licenses screen, regenerate notices against the actual shipped dependency graph, and inventory native binaries. MIT is not authorization to redistribute provider accounts, SDK services or third-party content. [Pinned license](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/LICENSE), [notice generator](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/scripts/sync-third-party-license-notices.ts).

Retain `apps/desktop/src/{boot,main,preload}.ts`, Electron service wrappers and updater machinery. Reconfigure `scripts/build-desktop-artifact.ts`, `.github/workflows/release-desktop.yml`, update-feed policy, app IDs, protocol handlers, icons, app-data directories, keychain namespaces, publisher identity and telemetry destinations. Never ship an updater that installs upstream T3 binaries or reads its private state. The packaging script uses Electron Builder with NSIS, DMG and AppImage targets, stages native helpers, and has separate Windows server-ASAR handling. Its Windows signing path uses Azure Trusted Signing. The release workflow also expects Clerk/relay configuration: these dependencies need explicit local-only configuration or removal, not inherited production endpoints. [Build source](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/scripts/build-desktop-artifact.ts), [release workflow](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/.github/workflows/release-desktop.yml).

First target Windows x64 with a signed installer; declare other OS/architecture support only after native packaged smoke tests. Signing identity and service eligibility are separate prerequisites; macOS needs signing and notarization. Retain `electron-updater`, rather than substituting Electron's different built-in updater protocol. Own HTTPS feeds and stable/beta channels; test interrupted downloads, wrong signatures, upgrade migrations and restore before release. Update only at a safe checkpoint. Database rollback needs a compatible backup, not merely an older executable. [Electron signing](https://www.electronjs.org/docs/latest/tutorial/code-signing), [upstream updater wrapper](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/apps/desktop/src/electron/ElectronUpdater.ts).

Maintain an untouched upstream tracking branch and a small, documented downstream patch series. Review upstream changes weekly; integrate selected compatible batches into a staging branch, accelerating security fixes. Record upstream SHA, downstream changes and schema version per release. Preserve upstream provider/reconnect/approval tests and add domain contracts. Avoid global renames of internal package namespaces. Assign explicit ownership for provider compatibility and desktop releases; this is recurring engineering work. A hidden reproducibility issue: the inspected release workflow says staged installs run without a lockfile. Freeze or record those resolved graphs too. Do not promise inexpensive maintenance or automatic merges.

## One shared domain, every module visible immediately

Register Brief, Evidence, Strategy, Product, Creator Discovery/Partnerships, CRM, Launch, Media, Publishing, Feedback, Export and Help in the first dashboard. Each has an explanatory screen, inputs/outputs, dependencies, release milestone, capability requirements, and acceptance criteria from day one. Unimplemented actions show their named implementation gate; they never pretend to run.

Shared objects: `BusinessProject`, `Audience`, `Problem`, `Offer`, `Source`, `Claim`, `Decision`, `Person/Organization`, `CreatorProfile`, `Relationship`, `Consent/Suppression`, `ArtifactVersion`, `Campaign`, `Channel`, `Publication`, `FeedbackItem`, `Experiment`, `Task`, `Run`, `Approval`, and `UsageReservation`. Use stable IDs and revisioned references. A creator profile is evidence attached to a person, not a duplicate CRM identity. Outreach belongs to a campaign and relationship; media variants belong to artifact versions; publication receipts identify exact versions and destinations; feedback links back to the offer and creates revision tasks. Preserve rights, provenance and deletion policies across these relationships.

Implement three independent state dimensions:

1. **Software release:** `planned → available`, version/platform scoped, with an independent operational-disable reason. Development tracking may use in-progress/blocked/completed, but “completed development” does not mean released to this installation.
2. **Per-project module progress:** `planned → available → in-progress → completed`; prerequisites determine availability. `available|in-progress → blocked` records a typed reason and previous state. Resolution returns to available or in-progress. Completed work reopens through a new revision when inputs change; preserve its prior completion record. Failure/cancellation belongs to step runs and normally blocks resumable module progress.
3. **Entitlement:** `not-required|granted|missing|expired`, evaluated independently of release and progress. Buying access cannot make unimplemented software available. Expiration cannot erase completed artifacts; keep local viewing/export working.

Start eligibility is the conjunction of shipped capability, satisfied dependencies, entitlement where relevant, usable connection, scoped permission and budget. Store an ordered event, actor, reason, input revision and evidence of acceptance on every transition. “Available” means ready to start; “completed” requires recorded checks and approvals, not an agent's sentence. A publishing module can be shipped yet blocked by missing credentials while its paid entitlement is irrelevant.

## Explicit implementation milestones

All modules belong to this delivery plan, with dependency edges fixed up front:

- **M0 — desktop foundation:** independently named packaged fork; entire module registry/dashboard; state contracts; local persistence; exact provider controls; basic help; install/restart/recovery gate.
- **M1 — evidence and decisions:** Brief, Evidence and Strategy workflows plus the shared recommendation service. Gate: retrievable citations, contradictory evidence, budget stops and stale-result handling.
- **M2 — product production:** Product, Export and document QA; first complete guide/workbook; initial Media asset registry and rights records. Gate: editable, versioned, validated export and crash-safe recovery.
- **M3 — audience operations:** Creator Discovery, Partnerships and CRM activate together; Launch planning/drafting and feedback capture connect to the same offer/contact graph. Gate: provenance, deduplication, suppressions and no accidental sends.
- **M4 — distribution and learning:** bounded Media generation, approved Publishing integrations, launch execution, feedback import and experiment/revision loop. Gate: sandbox receipts, exact-payload approval, unknown-outcome reconciliation and media quality checks.
- **M5 — optional execution expansion:** hosted workers/billing and scoped remote access activate capabilities already represented in the registry. Gate: tenancy, accounting, revocation and cross-version transport tests. Local workflows remain usable without cloud login.

These are engineering unlocks, not a customer funnel forcing every project through a linear sequence. Independent modules may run concurrently once their actual inputs exist. Every milestone carries the same evidence, recommendation, budget and review contract.

## Research and recommendations throughout the product

Build one daemon-owned service invoked by every module: `recommend(context, decisionType, evidencePolicy, budget)`. Triggers include meaningful edits, stage entry, stale evidence and explicitly configured schedules. “Continuous” means bounded refresh and synthesis, not an endless agent loop. On a sleeping/offline desktop, display last research time and queued work; cloud scheduling requires separate opt-in execution.

Pipeline: query planning → authorized search/fetch → canonicalization/deduplication → extraction → claim-source linking → contradiction/freshness checks → ranked choices → scoped action proposal. Save canonical/final URL, title, publisher, retrieval and publication dates when known, content hash, short supporting passage/locator, access status and rights notes. Verify links and passage support independently of the drafting model. Label inaccessible, secondary, stale and conflicting sources; a working URL does not establish truth. Never fabricate citations for search snippets that were not inspected.

Recommendations explain evidence, assumptions, alternatives, confidence limits, cost and reversibility for niche selection, product structure, creator fit, outreach, pricing hypotheses, media, publishing and feedback responses. Record acceptance/override reasons. Cache by context/evidence revision. Enforce project and run ceilings for money, tokens, searches, pages, media jobs, runtime, recursion and concurrency; reserve budget before child dispatch. Unknown CLI costs remain unknown, with hard operational limits. Retry only bounded transient reads; never duplicate uncertain sends.

## Exact providers, modes and tool-fleet boundaries

Preserve T3's actual wire selection `{instanceId, model, options?}`; options are descriptor-based selections, not one universal effort dropdown. Delegation uses `target.providerInstanceId`, `model`, and `options` (array or record accepted), optionally environment/project, with inherited defaults. Discover capabilities on the execution host and explicitly pin settings for each planned worker. Store requested/effective identity, options, account-instance reference and adapter/catalog version. Unsupported or changed settings stop with explanation. Do not hardcode the example Sol/Astra selections into every user's catalog. [Selection schema](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/packages/contracts/src/modelSelection.ts), [delegation schema](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/packages/contracts/src/orchestratorMcp.ts).

Keep Supervised, Auto-accept edits, Auto and Full access with provider-specific availability, plus interaction/planning controls. Upstream initially defaults to Full access; change novice startup to Supervised and add “Recommend and do safe work” as a separate workflow policy. That policy preauthorizes bounded research and reversible typed document operations inside project storage. It does not mislabel provider Supervised mode or bypass its approvals. External sending, publishing, spending, destructive operations and privilege expansion need concrete-payload authorization. Advanced users retain supported T3 controls. [Permission behavior](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/docs/user/permission-modes.md).

The tool fleet has distinct owners: provider-native tools execute within provider sessions; T3 orchestration coordinates children and lifecycle; worktree/project/PR tools manage code; preview/HTML/attachment tools expose browser and artifacts; device/environment tools address execution hosts; connected service adapters supply business data and publication. The pinned MCP toolkit tree confirms these families, not that every connector is configured. Add a capability registry mapping each tool to lane, permissions, data destinations, cost and module use. Discovery is not authorization. [Toolkit tree](https://github.com/pingdotgg/t3code/tree/7d71f852a8edd298ffde67c295760c286a71a27c/apps/server/src/mcp/toolkits).

Document edits should use typed revision-checked operations and trusted exporters. Generated code, package installation, macros and executable previews require a distinct execution lane with isolation and narrower credentials. Git worktrees isolate changes, not hostile processes. Research content cannot grant permissions. Keep remote content without Node integration, validate IPC senders and isolate previews. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security).

Desktop owns files, SQLite, credentials and CLI sessions. Browser/mobile clients control an authenticated host; they do not execute local CLIs themselves. Cloud workers own separate files, credentials and billing, with explicit transfer manifests. Preserve T3's connection boundary, but do not equate upstream device access with project-scoped novice authorization. [Connection architecture](https://github.com/pingdotgg/t3code/blob/7d71f852a8edd298ffde67c295760c286a71a27c/docs/internals/connection-runtime.md).

The largest remaining risks are inherited shell authority, non-Git/binary versioning, source licensing and extraction reliability, provider drift, cross-platform native packaging, duplicated external effects, and schema migrations during background work. A fork reduces platform reconstruction; it does not supply the business state machine, citation verification or safe automation policy. Those are the product's principal new engineering responsibilities.
