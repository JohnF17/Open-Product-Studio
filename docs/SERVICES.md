# Services, authority and operating stages

Design decision, 13 November 2026. This is an original implementation contract, not a list of installed services or an account recommendation. The [roadmap](ROADMAP.md) and [work packages](WORK-PACKAGES.md) govern activation. [Payments](PAYMENTS.md) owns finance policy; [project experience](PROJECT-EXPERIENCE.md) owns navigation and recovery. Keep vendor-neutral ports and a small number of services with an actual need. A vendor name, open-source license or green documentation check does not establish backend authorization, account approval or operational safety.

## Minimum useful topology

The local product needs the retained T3 Electron/React shell, authenticated Node/Effect engine, SQLite, immutable asset files and the user's selected supported provider or local model. Installed editing/export and a labeled editable example need no Studio account or network. The complete module registry remains visible; its later connectors are separate gates, not mandatory purchases.

A first sale adds one eligible creator-owned checkout/delivery destination and its support route. It need not add Studio hosting, campaign mail, a creator partnership, a connector aggregator or a platform-owned LMS. Manual setup/import/export is a supported, labeled route when the official API cannot write a product or file.

Optional hosted work adds Clerk identity, Convex business state/private storage, one qualified isolated worker host and the conditional direct billing adapter in PAYMENTS.md. Cloudflare supplies domain/TLS/static edge only where deployment needs it. Keep existing outbox/coordination and indexed search before introducing another database, queue engine or search service. M7/M8 integrations, councils and the single later Dot remain in scope, each with their own readiness and operations evidence.

Price changes or exhausted allowances block/requote affected work; they never authorize another provider or an automatic purchase.

## Identity and connector boundaries

Clerk is the preferred hosted default, replacing the earlier Better Auth proposal. The domain remains provider-neutral. Convex must validate the configured issuer/audience and authentication state, then check internal membership, role, parent and object ownership on every exposed function. A signed-in screen is not backend authorization. WorkOS is an alternative only after a concrete requirement and migration decision; do not run two identity authorities or create accounts now. The official [Convex Clerk integration](https://docs.convex.dev/auth/clerk) supplies the integration path, not our authorization policy.

Prefer hosted/system-browser sign-in with a separately qualified desktop bridge. Test packaged origins, custom protocol/IPC/CSP, state/nonce, allowlisted one-use callback, supported methods, secure main-process storage and session recovery without widening the trusted renderer's CSP/IPC or indiscriminately embedding remote auth UI there. The [Clerk Electron reference](https://clerk.com/docs/reference/electron/overview) identifies a beta SDK with process-specific integration: it is a separately pinned and qualified alternative, not a mandatory shell scaffold. Its online prebuilt UI cannot be a dependency of local editing/export. Local engine authentication, paired-device grants and cloud identity remain separate.

Do not enable Clerk Billing alongside the direct billing proposal. Clerk's [billing overview](https://clerk.com/docs/guides/billing/overview) and [account credits](https://clerk.com/docs/guides/billing/account-credits) describe separate billing concepts; identity adoption does not replace payer-bound reservations/settlement or creator commerce. A billing product change would require an explicit migration with one financial authority.

Every `ConnectorBinding` carries server-derived owner/workspace, verified external provider/account, environment, resources/scopes, credential generation and revocation epoch. Bind OAuth setup to the initiating authenticated actor and a short-lived one-use state. A project switch during login cannot redirect the callback to another project. Events route from trusted endpoint/subscription/account mappings and namespaced object/effect IDs; signed B events carrying A metadata must not mutate A. Reconnection to another account cannot adopt earlier account operations. Separate personal-channel, creator-commerce and Studio-billing secrets and replay namespaces.

Composio stays optional. Its [session documentation](https://docs.composio.dev/docs/how-composio-works) describes broad discovery defaults, connected-account selection and execution state. Our design filters toolkit/tools, derives the user/workspace principal on the server, pins the exact verified connected account and brokers execute/meta/proxy/auth-management paths, including direct hidden-tool calls. Disable unneeded sandbox and memory/log retention; qualify any allowed sandbox with WP40. Discovery must not auto-connect, publish or grant scopes. A success envelope is not the intended external result. Adopt it only if a real multi-connector requirement outweighs another data recipient and operational dependency.

## Data flows and custody

**Local:** renderer intent → authenticated engine → validated domain command/one SQLite transaction and outbox → scoped provider/tool → immutable artifact/receipt → project view. Ordinary edits need neither a thread nor Git. Live research/inference waits honestly when offline; installed exports continue. Sources and model output cannot grant authority.

**Hosted:** explicit data preview and transfer → Clerk-authenticated Convex workspace checks → verified artifact manifest and ownership epoch → authorized payer/grant/reservation → isolated Node/API worker → scoped commercial provider → trusted usage/artifact receipts → current cloud authority. Cloudflare edge can serve static UI/TLS; it cannot replace those checks. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) do not prove arbitrary CLI/Chromium/native-renderer compatibility. Hosted credentials never come from a copied consumer CLI session.

**Creator checkout:** reviewed local/cloud offer + exact merchant/mode/artifact mapping → explicit publication/manual setup → provider checkout → verified account-bound event/history → order/access projection → provider-held buyer delivery. BillingOrganization service packs do not fund creator-sale ledgers; buyer identity is not a Studio seat. Desktop shutdown must not strand a paid download.

**Transfer in either direction:** fence new dispatch; pin content/asset snapshot; inventory queued native runs, active attempts, provider-held schedules/sessions, leases, Unknown actions and account generations. Cancel with evidence, retain a single named custodian or reconcile/adopt under the same verified provider/account before any conflicting destination action. Preserve operation/attempt IDs and unresolved resource fences, not credentials or reusable approvals. Commit a new ownership epoch only once; route late receipts to current authority without replay or revival of the old writer. If remote custody is unresolved, block that action lane while allowing inspection/export. The same invariant governs Dot host moves.

## Exit, restore and operations

Compute exhaustion stops new paid work; storage/team lapse stops the affected service; revoked membership denies access; expired login requires reauthentication; an outage means remote bytes may be unavailable. These are different states. Legitimate owners receive an authenticated, non-paywalled read/export/handback window for retained latest content, proposed **30 days**, with capacity, deadline, backup and finance-retention terms finalized before hosted activation/checkout. Export never requires funded AI generation. Missing assets and retention expiry need an honest support/recovery result, not an empty successful bundle.

Offer verified local snapshots before/after transfer. Handback verifies current revisions/assets and operation custody before fencing cloud writes and assigning the local epoch. During outage, show the last verified cache time. An explicit offline content fork gets a new ID and no inherited approvals, balances or external operations; reconnect cannot auto-merge them or unfreeze the stale former local master.

Managed restore obtains a current deletion/revocation generation from an authority or journal outside the rewound backup before rebuilding indexes, summaries or queued contexts. Restored grants/device bindings/wakes stay inactive. With only an unmanaged old archive available, recover content into a review/quarantine state and explain that newer deletions cannot be known; do not promise non-resurrection from arbitrary archives. See WP07, WP18, WP34, WP56 and WP60.

Each connector's first activation needs an operator/backup or explicit provider support route, bounded ingress/backlog/rates/costs, retention, alerts, reconciliation, credential-compromise response and a customer-visible support path. Keep a credential-free outage runbook usable when the app/host is down. Inventory provider-side schedules, sessions, domain/number rent and renewals and prove pause/cancel. Stop in the UI is not universal remote cancellation. WP27/30 prove paid-but-not-delivered recovery with the desktop closed; WP62/65 independently exercise inbound storms and ongoing charges before their channels activate. WP37 later adds hosted-wide operations, not permission to skip earlier readiness.

Use payment receipts and redeemed service costs for contribution, and separately account for unspent/reserved obligations. For each topology name who pays the zero-usage floor: ingress, retained assets/backups/export grace, idle browser/workers, domains, mailboxes and numbers. Test low-use, normal-use, high-retry, abusive-ingress and zero-new-top-up cohorts. No face-credit subtraction, optimistic free tier or unlimited claim replaces measured economics.

## Evidence stages and acceptance ownership

Every canonical acceptance item has an `acceptanceEvidence` entry with phase and producer; these entries are design metadata, all `not-run`. Component fixtures establish buildable interfaces. Integration evidence uses the named packages, actual packaged readers or separately authorized account tests. Public-release evidence enables the exact build/action only after all applicable conditions and independent review. No one can close a later gate by marking a component complete.

WP02 component packaging does not consume WP07 output; populated Studio restore remains a later integration/release gate. E4 splits pre-build rights/provider/terms/budget decisions from public-paid economics/operations produced by WP37. WP35/36 fixtures can proceed, while public paid checkout/dispatch remains disabled. No reverse dependency is added to hide an acceptance cycle. Optional adapters and creator inputs use conditional dependencies; direct products/manual feedback keep useful independent paths.

Qualification receipts bind executable/driver/runtime digest, model/route, permission configuration, OS/sandbox and tool-schema version. Changes invalidate affected execution authority while preserving saved choices. Distribution/extension trust metadata has signed expiry/revocation generation and rollback protection. Classify intentionally offline lanes separately: the proposed 24-hour freshness limit applies only to grants/extensions whose accepted policy requires current remote revocation, and blocks only that scoped execution when stale. Core local execution and already-qualified user-owned CLI/API/local-model adapters gain no Studio sign-in or central heartbeat dependency; provider requirements and verified compromise responses still apply. Test this distinction with both stale-extension denial and continued offline local-model work/editing/installed export. Recovery of compromised publisher/update keys needs an independently authenticated path, never permanently disabling signatures (WP02/39/53).
