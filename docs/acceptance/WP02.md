# WP02 working evidence

Against the [initial upstream baseline](../upstream/baseline-7d71f852.json) on November 19, the first Studio desktop change assigned different Electron profile directories to development and production: `open-product-studio-dev` and `open-product-studio`. Boot assigns both Chromium user data and session data before acquiring the single-instance lock. The fork removes T3's legacy profile key copy, local-storage reader and migration IPC. Ordinary first launch also skips the inherited CLI installation and PATH change.

Five focused suites exercised pre-ready initialization, profile selection, fixture boot, Clerk initialization and error handling. On Windows, 29 tests passed and the POSIX permission test was skipped. The tests used synthetic T3 sentinel profiles, an isolated environment and mocked external services. The source build and packaged binary documented under [WP01](WP01.md) are the pristine upstream baseline.

## Studio runtime on the rebased source

The Windows runtime work starts at foundation `0d98e9192f11`. The four local identity commits end at `3435df505b`. They establish these default boundaries for the desktop and its native server child.

| Resource | Studio behavior |
| --- | --- |
| Chromium and engine state | Electron puts the production profile in `%APPDATA%\open-product-studio` and the source-development profile in `%APPDATA%\open-product-studio-dev`. The engine defaults to `~/.open-product-studio`. An explicit `STUDIO_HOME` selects the engine base, including synthetic profiles. An inherited `T3CODE_HOME` cannot select the desktop engine's base. |
| Windows application and URI | Windows uses the app ID `org.openproductstudio.desktop` and the scheme `open-product-studio:`. Source development uses the `.dev` app ID and `open-product-studio-dev:`. Keyless first launch acquires an Electron single-instance lock and leaves OS scheme ownership to the installer. NSIS uninstall checks the stored command before removing its scheme association. |
| Host integration | First launch does not install a CLI or add a PATH entry. The optional Studio CLI uses `open-product-studio` and a previously installed Studio shim can be refreshed. Machine policy reads `HKLM\SOFTWARE\Policies\OpenProductStudio\Desktop`. |
| Local services | The server selects bundled model metadata at startup and a local analytics service with no external sink. The keyless local configuration skips the Clerk renderer bridge. Legacy hosted configuration requires `STUDIO_ENABLE_HOSTED_CONNECTIONS=1`. Adopting exporters from OTLP environment variables requires `STUDIO_USE_OTLP_ENV=1`. A configured exporter or authenticated hosted connection would require separate qualification. |
| Packaged child process | A packaged desktop selects bundled assets and ignores an inherited Vite development URL, upstream server port, trace file and auto-bootstrap setting at the appropriate process boundary. Its own explicit fixture port is `STUDIO_DESKTOP_PORT`. Windows also clears mixed-case spellings of the patched child variables. |
| Releases | Local package construction has no default upstream update repository. The bundled project license remains in the package inputs. The technical names used for wire protocols and internal workspace imports remain compatible with the upstream engine. |

Tests ran in a dedicated checkout using Node 26.13.1 for Windows x64, the pinned local dependency cache, synthetic home and app-data directories and an upstream sentinel. The harness supplied a short Windows process-variable allowlist, disabled optional telemetry and auto-update and kept the credential environment empty. Test services used fixtures. The source tests exercise Windows settings, mocked Electron and updater services and fixture storage. The broader CLI shim suites include POSIX-only executable and PATH assumptions that fail when run unfiltered on Windows. Live WSL/POSIX CLI installation, an OS credential-vault audit, external telemetry capture and signing-key management each require their own evidence. Side-by-side installation, restart, uninstall, profile retention and installer registry ownership also require an installed lifecycle run under an isolated Windows account. Existing production icon assets are inherited from upstream.
